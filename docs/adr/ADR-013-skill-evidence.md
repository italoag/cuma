# ADR-013 — A skill's evidence is its digest and a signature, checked at install

**Status:** Accepted

*Amends [ADR-008](ADR-008-skill-security.md), whose principle this implements.*

## Context

ADR-008 decided that trust is derived from evidence, never from a claim. The
first implementation did not honour it: a manifest carrying non-empty
`checksum` and `signature` fields was rated `Verified`. Nothing checked either
field against anything. A manifest could talk itself up — the exact failure
ADR-008 exists to prevent — and skills were only ever metadata, so there were no
bytes a checksum could have been checked against.

## Decision

A skill is a directory of files (`skill.toml`, `SKILL.md`, anything they refer
to), and trust is computed from those files at install time:

- **Digest.** SHA-256 over every file in a fixed order — relative path, a NUL,
  length, bytes — so renaming, moving bytes between files or adding an empty
  file all change it. Symlinks are refused rather than followed.
- **Signature.** `skill.sig` holds `ed25519:<key-id>:<base64>` over the digest
  string. It verifies (with `verify_strict`) against keys the operator lists
  under `[skills.trusted_keys]`, or it does not.

| Evidence | Trust |
|---|---|
| Built into the binary | `Trusted` |
| Valid signature by a configured key | `Trusted` |
| Files match the digest an HTTPS index published | `Verified` |
| Fetched over TLS or from a local directory, nothing more | `Community` |
| Generated by CUMA | `Untrusted`, whatever else is true |
| Invalid signature, or digest mismatch | **refused** |

A signature by a key nobody configured proves nothing and earns nothing. A
registry's provisional label on its search results is display only; installation
ignores it and lets the evidence decide.

Installation fetches into a staging directory, examines it there, and only then
moves it into place and records it in `installed.json`. Nothing in a skill is
executed at any point. An update is verified like a first install; one that
fails keeps the installed version, and one whose trust fell is installed
disabled.

## Consequences

- `Trusted` now means something a person can check: `cuma skills verify <dir>`
  prints the digest and what the signature showed.
- Publishers need a key. `cuma skills keygen` and `cuma skills sign` exist so
  that signing is not the reason skills go unsigned.
- Git registries publish no digest, so an unsigned skill from one is
  `Community`. That is the honest rating for "fetched over TLS from somewhere".
- There is no revocation: removing a key from configuration is the only way to
  stop trusting what it signed. Recorded in the roadmap.
