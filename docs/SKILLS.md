# Skills

A skill is packaged know-how: instructions an agent is given for a kind of
task, plus the capabilities they cover. It closes a capability gap — the
planner needs something no registered agent is known to provide — or simply
makes agents better at something a person cares about.

A skill's instructions reach an agent's prompt, so installing one is a trust
decision. The rules are blunt: **nothing is installed until its files have been
verified, trust comes only from what verification shows, and nothing a skill
contains is ever executed by CUMA.**

## A skill on disk

```text
rust-debug/
├── skill.toml   id, name, capabilities, requested permissions
├── SKILL.md     the instructions
├── skill.sig    optional: ed25519:<key-id>:<base64 signature>
└── …            anything the instructions refer to
```

```toml
# skill.toml
id = "rust-debug"
name = "Rust debugging"
description = "Interpret compiler and borrow-checker errors"
version = "1.0.0"
capabilities = ["debugging"]
permissions = ["filesystem:read:./src", "shell:run:cargo"]
```

A directory with only a `SKILL.md` whose front matter has `name` and
`description` — the Agent Skills layout — is accepted too. It declares no
capabilities, so it is never auto-installed for a gap; once enabled, its
instructions accompany every task.

## Installation

```
registry ── fetch into staging ── digest + signature ── validate ── move into place ── installed.json
                                                             │
                                                        refused: nothing lands
```

Installed skills live in `.cuma/skills/<id>/` (or `skills.install_dir`), and
`.cuma/skills/installed.json` records each one's digest, trust, source and
whether it is enabled. That record is what `cuma skills list` reads, in this
process or the next.

## Trust

Computed from the files, never read from the manifest. See
[ADR-013](adr/ADR-013-skill-evidence.md).

| Evidence | Trust |
|---|---|
| Built into the binary | `Trusted` |
| Signed by a key in `[skills.trusted_keys]`, signature valid | `Trusted` |
| Files hash to the digest an HTTPS index published | `Verified` |
| Fetched over TLS, or from a local directory, nothing more | `Community` |
| Generated by CUMA | `Untrusted` — always |

**Refused outright:** an invalid signature; files that do not match a published
digest; symlinks; more than 1 000 files or 10 MiB; an id that is not a plain
identifier; unrestricted permissions (`shell:unrestricted`,
`filesystem:write:/`, `network:unrestricted`, `credentials`, `keychain`,
`env:read:*`); scope-escape patterns (`..`, `$(`, backticks, control
characters); non-TLS remote sources; unknown manifest keys.

A signature by a key nobody configured proves nothing. The `checksum` and
`signature` fields a manifest may carry are ignored for trust: they are
claims.

## Enabled

An enabled skill's `SKILL.md` is added to the prompt of every task needing one
of its capabilities, most trusted first, labelled by trust, within a 12 000
character budget.

| How it arrived | Enabled |
|---|---|
| `cuma skills install` | Yes — the command is the approval |
| Auto-installed for a gap, within policy | Yes |
| `cuma skills create` | **No**, and it cannot be enabled while `Untrusted` |
| An update whose trust fell | Disabled |

`cuma skills disable <id>` stops a skill guiding agents without removing it.

## Registries

```toml
[skills]
registries = [
  "builtin",                                   # ships with CUMA
  "local",                                     # .cuma/skill-sources/
  "git+https://github.com/acme/skills",        # any repository of skill packages
  "https://skills.example.com/index.json",     # an index publishing digests
]
```

**Git** repositories are cloned shallowly into `.cuma/cache/skills` and
searched up to three directories deep. HTTPS only; credential prompts are
disabled. They publish no digest, so their skills are `Community` unless
signed.

**HTTPS indexes** list each skill's files and the digest they must hash to:

```json
{ "skills": [ {
    "id": "rust-debug", "name": "Rust debugging", "version": "1.2.0",
    "capabilities": ["debugging"], "permissions": ["shell:run:cargo"],
    "sha256": "sha256:9f86d0…",
    "base_url": "https://skills.example.com/rust-debug/",
    "files": ["skill.toml", "SKILL.md", "skill.sig"]
} ] }
```

File paths that leave the skill's directory are refused.

## Signing, for publishers

```bash
cuma skills keygen                                     # prints a key pair
cuma skills sign ./rust-debug --key-id acme --key-file secret.key
cuma skills verify ./rust-debug                        # digest, and what the signature shows
```

Consumers trust the key by id:

```toml
[skills.trusted_keys]
acme = "base64-public-key"
```

## Policy

```toml
[skills]
enabled = true
auto_install = "trusted-only"   # never | trusted-only | verified
allow_creation = false
```

| Policy | Installs for a gap without asking |
|---|---|
| `never` | Nothing |
| `trusted-only` *(default)* | `Trusted` |
| `verified` | `Trusted`, `Verified` |

Anything else comes back as `NeedsApproval`, with the validation report.

## Built-in skills

| Skill | Capability |
|---|---|
| `git-workflow` | `version_control` |
| `cargo-toolchain` | `testing`, `shell_execution` |
| `test-runner` | `testing` |
| `doc-search` | `research` |

Each installs as a real package with instructions, like any other skill.

## Commands

```bash
cuma skills search rust
cuma skills inspect rust-debug     # fetch, verify, validate — then discard
cuma skills install rust-debug
cuma skills list
cuma skills enable | disable | remove <id>
cuma skills update [<id>]          # re-verified; a failing update keeps the old version
cuma skills create <capability>    # needs skills.allow_creation and a provider
cuma skills verify | sign <dir>
cuma skills keygen
```

The TUI's Skills screen lists installed skills; space enables or disables one.
